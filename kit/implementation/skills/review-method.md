# Reviewing Skills and Capabilities

A short maintenance loop for keeping the [selected catalogue](README.md) useful. Review additions when a recurring task, credible upstream example, repeated friction or a material product change gives a reason. There is no requirement to evaluate every skill or run a full comparative pilot before configuring a selected provider capability.

## 1. Establish fit and source

Name the job and what a useful result must achieve. Start with the host provider's native capability or own published package. Use its GitHub source to identify a published offering; check package authorship separately from marketplace inclusion. Official product documentation establishes native features and controls. A local cache can establish neither the upstream catalogue nor source parity.

Inspect the selected workflow and relevant dependencies: additional tools, scripts, hooks, services and any persistence or publication effects. Scale inspection to what will actually be enabled or executed. Claude enables every skill in a plugin together. Assess the whole bundle, even when one skill motivates selection; verify other harness controls separately. Provider provenance does not prove output quality.

Keep provider skills in their own harness. Independently authored third-party additions can later be assessed for both surfaces. Leave the authored voice skill outside this provider review.

## 2. Choose and configure

Record the source link, intended job and On or Off choice in the catalogue. Put the target surface, supported controls, selected revision where inspectable and verification state in the appropriate platform guide. Record unknowns without creating another register.

Use actual host enablement controls. In Claude, an enabled plugin exposes all included skills and a disabled plugin is unavailable to select in chat. Choose whether to keep the whole bundle enabled; do not introduce an artificial task-only state or require toggling around each job. Use provider-managed delivery and supported update controls, not manual uploads. If that route is unavailable, leave the addition undeployed and record the limitation. Do not edit managed caches or rely on instructions to suppress discovery.

Prepare an exact change and preserve a way to restore the affected settings before live deployment. Keep connector accounts, permissions and unrelated configuration out of the change unless explicitly included. Existing authority covers its named batch; repository documentation alone does not authorise live changes.

## 3. Verify useful use

After an authorised change, verify saved state and availability in a fresh session on the actual surface. Distinguish enabled, exposed, loaded and successfully exercised; record only what can be observed.

Use a representative real task to check output quality and correction effort. Inspect the rendered artifact when layout matters; check calculations, source fidelity and editability where relevant. Include an unrelated exploratory request to detect unwanted activation. Reuse a relevant [composition example](../../evals/capability-composition-probes.md) or [boundary fixture](../../evals/README.md) if it addresses a real concern.

A matched native-versus-addition comparison is useful when the addition's value, overlapping behaviour or cost is uncertain. Hold the brief, model/effort, tools and inputs comparable, start fresh sessions and repeat close or inconsistent results only when it could change the decision. It is not a universal admission gate.

Judge the accepted task: usefulness, factual quality, repairs, human editing time, latency and usage where reported. Do not infer token savings from installed skill count, file bytes, shorter answers or metadata-only exposure. Unreported usage stays unknown. Keep capable thinking-partner models for substantive judgement; changing the model is a separate comparison. See [model guidance](../platforms/model-guidance.md).

## 4. Refine from evidence

Retain a useful selection, narrow its activation, or leave it off when it adds little. Record material deployment results once in [governance evidence](../../../governance/evidence/README.md) and link them from the platform baseline. Ordinary use need not generate a new formal record every time.

Revisit a selection after a meaningful model/host/package change or repeated friction. Test removal of a suspect workaround without weakening personal ownership or authority rules. A release announcement or star count starts consideration, not automatic adoption, updates or deletion. A small successful trial supports that use case, not a universal performance claim.
